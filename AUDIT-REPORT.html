Data loss & storage leaks P0 · all fixed

Five defects that silently destroyed user data or leaked paid storage forever. These were the reason for the whole exercise.

P0-1Fixed

Deleting a folder permanently destroyed every file inside it

app/api/folders/[id]/route.ts:444 → models/Folder.ts:293

Folder delete ran a bare File.deleteMany({ folder }) — no soft delete, no deleteMessage, no version cleanup, no Blob cleanup. Files vanished instantly and irreversibly, while single-file delete correctly went to trash. Every file in the folder also orphaned its Telegram document.

Now: softDeleteRecursively() stamps the whole subtree — folders, files and chunk parts — with one trashExpiresAt, so it expires together and is restorable. Every listing, resolution and duplicate-check path was audited to filter deletedAt. Restoring a file brings its folder chain back too, so it doesn't return invisible.

P0-2Fixed

A Mongo TTL index was racing the cleanup job and eating the cleanup

models/File.ts:207

A TTL index on trashExpiresAt meant the mongod TTL monitor deleted rows on its own schedule — without running deleteMessage. Trash cleanup only ran opportunistically when a user opened their trash page. Any file trashed by someone who never revisited it orphaned its Telegram document permanently.

Now: no TTL index. Expiry has exactly one owner — the sweep in the new lib/maintenance.ts, started once from lib/db.ts. It also reaps expired share links, which had no cleanup at all.

P0-3Fixed

“Delete my account” deleted nothing

app/api/auth/confirm-deletion/route.ts:84,90,95,99

The transaction filtered on userId. Neither schema has that field — it is owner. Mongoose passes unknown keys through, so it matched zero documents: the User and the verification codes were deleted and the transaction committed, while every file, folder, version and Telegram document survived, unreachable by any UI and billed indefinitely.

Now: filters on owner, and reclaims storage through the shared purge. The admin user-delete path had the same leak and now collects documents before its transaction and reclaims after it commits.

P0-4Fixed

“Delete forever” leaked the cached Blob

models/File.ts:565 → purgeStoredResources()

Four different paths each re-implemented a subset of “delete chunks → delete messages → delete rows”. Only two of them deleted the Blob, so deleting a file from the trash view leaked its cached object. Whatever each copy forgot, it leaked silently.

Now: one primitive — File.purgeStoredResources() — reclaims Telegram documents, Blob cache, chunk parts and version rows. Every “delete forever” path calls it: trash empty, trash single-delete, admin trash, the expiry sweep and both account-deletion routes. Failures are logged instead of swallowed.

P0-5Fixed

Versions were invisible to quota and never pruned

models/File.ts:408 · app/api/files/[id]/versions/route.ts

getStorageUsage summed only live files. Version rows are separate Telegram documents, so a user could hold unbounded history for free, consuming storage no limit accounted for.

Now: versions count toward quota, capped at 10 per file — oldest pruned with their Telegram messages, so the cap doesn't trade a quota leak for a storage leak.

Broken behaviour & security P1 · all fixed

Things that did work — just not the way anyone reading the code would assume.

P1-1Fixed

WebDAV ranged reads silently didn't work for any large file

lib/webdav.ts:336

The chunked branch called streamChunkedFile() without ever calling writeHead. Every file over 50MB came back as an implicit 200 with no Content-Type, Content-Length, ETag or Accept-Ranges — and a ranged request was answered 200 instead of 206. Resumable and ranged reads are the entire reason to mount a cloud drive.

Now: headers are written once the chunk set is verified complete (so a missing-chunks 404 can still be sent), and the 206 status and Content-Range are correct.

P1-2Fixed

Version-uploading a >50MB file silently did nothing

app/api/files/[id]/versions/route.ts:181

It pointed fileId at a new Telegram document but left chunkedId/totalChunks intact, so downloads kept assembling the old parts while size claimed the new ones. The uploaded document was orphaned and the old bytes were never snapshotted either.

Now: an honest 400 CHUNKED_VERSION_UNSUPPORTED before anything is uploaded. Real chunked re-versioning remains unimplemented — that is a known, documented limitation rather than a lie.

P1-3Fixed

Verification codes were logged in plaintext, in production

forgot-password · request-deletion · vault/recover-request

console.log(... ${code}) ran unconditionally, so password-reset codes went to the production log — anyone with log access could take over any account. Codes were also generated with Math.random() and stored in plaintext, and the only brute-force brake was an IP limiter trusting a client-supplied X-Forwarded-For.

Now: logging removed; the dev-only body echo reads the validated env; generation is crypto.randomInt; codes are stored as an HMAC-SHA256 digest via a pre-save hook (so no creation site changed); and each code stops matching after 5 failed attempts, which travels with the code rather than the IP.

P1-4Fixed

WebDAV auth had no rate limiting at all

lib/webdav.ts:107

The handler ran bcrypt.compare and never consulted any limiter — unthrottled brute force against a mounted-drive endpoint.

Now: throttled by the account being attacked rather than client IP, since the Pages Router handler only has an IncomingMessage and a spoofable header should not be able to rotate the bucket.

P1-5Fixed

WebDAV LOCK was decorative

pages/api/webdav/[[...path]].ts:47

Locks lived in a module-level Map keyed by path alone — so one user's lock blocked another's — and no handler ever consulted it. PUT, DELETE, MOVE and PROPPATCH wrote through locks freely. No timeout, and every lock evaporated on restart: precisely when a client that had locked a resource expected it to still be there.

Now: a Lock collection keyed by owner+path with a TTL index. LOCK refreshes rather than duplicating and refuses to steal another principal's lock; UNLOCK validates the token; all four mutating methods enforce it and answer 423.

P1-6Fixed

69MB of debug dumps, committed and pushed — and lint couldn't see the source

commit ad2ac8b · eslint.config.mjs

28 byte-identical *-player-script.js files (~2.5MB each) landed in the tip commit, plus a 9.9MB vendored opencv.js being linted. ESLint reported 227,016 problems, of which exactly one was real source. That one hid behind the noise.

Now: files removed, patterns ignored, history rewritten and force-pushed (you approved this explicitly). Lint is 0 errors, 42 warnings — all genuine. Repo working tree: 76MB → 23MB.

P1-7Fixed

WebDAV conformance gaps that broke real clients

lib/webdav.ts · pages/api/webdav/[[...path]].ts

getlastmodified reported createdAt and File had no updatedAt at all — so a PUT-overwrite never changed the timestamp and sync clients missed updates entirely. PROPFIND's ETag was the escaped href while GET's was the _id. PROPPATCH parsed a <propertyupdate> body with the PROPFIND parser, so it always refused 403 with the container names (“propertyupdate”, “set”, “prop”). Malformed %-encoding threw URIError → 500. COPY/MOVE onto a name held by a hidden folder surfaced a raw E11000 → 500. And range parsing was duplicated verbatim in two files, neither handling suffix ranges (bytes=-N).

Now: a Mongoose-managed updatedAt on both schemas; unified ETag; a real parseProppatchProps() echoing the client's own qualified names; 400 for bad encoding; explicit 409 for collisions; and one shared range parser with suffix support, verified across 14 cases.

P1-8Fixed

YouTube calls could hang forever, and ignored client disconnects

lib/youtube.ts · app/api/youtube/download/route.ts

Every innerTube call used a bare fetch with no AbortController, so a stalled CDN connection pinned the request open indefinitely. The download route never read request.signal, so a client who navigated away left the server downloading and rotating URLs to completion. The fallback chain could run 2 VR + 1 ANDROID + 6 ytdl attempts unbounded. The 1GB cap was only checked against a known Content-Length, so an unknown-length stream bypassed it. And redirects were followed without re-validating the host, making the SSRF guard a formality.

Now: per-request timeouts, the client's abort signal propagated through resolution, rotation and both streaming paths (including destroying the ytdl stream), a 45s budget on the chain, a byte-counted size cap, and manual redirect following that re-validates every hop.

P1-9Fixed

Telegram's retry_after was ignored server-side

lib/telegram.ts:66,115

makeRequest threw immediately on a 429 without reading parameters.retry_after. Only the browser-side chunk uploader honoured it, so multi-part uploads and large downloads through the server failed avoidably under rate limiting.

Now: the server waits the interval Telegram asked for and retries once; TelegramError surfaces retryAfter.

Robustness, correctness & duplication P2 · 24 fixed

The long tail. Grouped by theme rather than listed one by one.

  • Regex injection in search. 11 sites interpolated user input straight into a Mongo $regex. “(“ made Mongo throw (a 500 instead of 400); “(a+)+$” could backtrack catastrophically; and metacharacters silently changed the query — searching report.pdf also matched reportXpdf. Now escaped and length-capped.
  • Internal errors returned to clients. Seven handlers echoed error.message — Mongoose and driver internals. Replaced with a generic message plus a code, detail left in the log.
  • Unbounded admin queries. The user export loaded every matching user plus an aggregation over all their files, and the computed-column sort loaded every user into memory. Both capped (10k / 5k) and report truncation — via headers for the export, since its body is a file.
  • ID validation. id.length !== 24 accepted 24 characters of any kind, so zzzz… passed and died as a CastError. Replaced with a hex check in 14 places.
  • Chunked downloads buffered the whole file in RAM. Up to 2GB resident per request — and a range request for a 1MB video header still fetched and assembled the entire file. New lib/chunk-stream.ts holds one implementation, shared by three callers, with a pure slicing planner verified against 35 window positions over unequal chunk sizes.
  • Failed and overwritten uploads orphaned Telegram documents. Three separate escape routes, including one where the 2GB cap throws mid-body and bypassed cleanup entirely.
  • Frontend: a thumbnail effect that re-fetched forever on failure; localStorage read in a useState initialiser causing hydration mismatches (now useSyncExternalStore); PDFs downloaded and parsed twice and re-parsed on every page turn; pdfjs statically imported into the chunk for all previews; Vietnamese users navigated out of the Vietnamese tree by five separate routes.
  • Accessibility: 10 password toggles with no accessible name, file and folder cards as bare <div onClick> (unopenable by keyboard), and two modals with no role, no Escape and no focus management.
  • Vietnamese parity: the document scanner was missing entirely from the Vietnamese dashboard — 15 wiring points present in English, zero in Vietnamese. Ported.
  • Dead code removed: LanguageBadge.tsx (119 lines), two never-called Telegram diagnostics, File.findDuplicates, File.findTrashByOwner, Folder.findByPath, Folder.getFolderTree, an unused isAdmin(), an unreachable success banner, a dead <Head> block that looked like working SEO, and a write-only validation state.
  • Duplication collapsed: two rate limiters into one; five copies of formatFileSize into one (three of them couldn't render TB, so 2TiB printed as “2048 GB”); two range parsers into one.
  • Docs: corrected Next.js 14 / React 18 claims to 16 / 19, fixed prerequisites, removed a Prettier claim with no Prettier, and documented the required migrations.

Corrections to the audit itself Verified, then revised

Three findings from the initial survey did not survive contact with the source. Worth recording, because acting on the wrong version would have made things worse.

Cookie-token logging was not a leak

Reported as leaking the session token to the console. The token cookie is HttpOnly, so document.cookie cannot read it. It was noisy and logged user data, but not a credential leak. Severity downgraded, logging removed.

“Missing validateOrigin” was not exploitable CSRF

The session cookie is SameSite=Lax, so a cross-site form POST does not carry it. Real severity: a consistency gap, not a live hole. The check is now applied uniformly anyway — it is cheap and its absence was the actual problem.

PreviewIndicator renders nowhere at all

Reported as showing English strings on the Vietnamese dashboard. It is imported by FileGrid but never rendered anywhere — those strings appear on no page. The dead import is gone; the orphaned component is left in place rather than deleted unasked.

Deliberately not changed Reasoning, not neglect

The quota check-then-write race remains

Every upload path reads usage then writes with no transaction, so two concurrent uploads can both pass and slightly exceed the limit.

Why I stopped: closing it properly means an atomic storage counter on the User — a new field every write path must maintain, including deletes, restores, versioning and the trash lifecycle. Getting that subtly wrong produces permanent quota drift, which is worse than a bounded overage that self-corrects on the next check. This needs its own focused change with its own tests, not a rushed tail-end edit.

Concurrent same-name uploads can still duplicate a name

Uploads avoid collisions with a name check plus a Date.now() suffix, which is not atomic. Two simultaneous PUTs to one path can both land.

Why I stopped: the fix is a unique index on File, which will refuse to build on any existing install that already has duplicate names — it needs a data audit first. Impact today is a duplicate listing, not corruption.

The COPY “quota double-count” was not a bug

Reported as a bug because reference copies share one Telegram document yet consume quota. But getStorageUsage sums every live row, so the check is consistent with how usage is computed. Making quota physical-only would change what every user's quota reads. That is a product decision, not a bug fix — flagged rather than made unilaterally.

The two register pages are still different implementations

The English page has a success screen; the Vietnamese page has a password-strength meter and live field validation. Converging them means picking one and losing features from the other — your call, not mine.

What you need to run Required

npm run migrate

Two schema changes cannot apply themselves, and skipping them leaves folder naming and trash behaviour broken on a database that already has data:

  • The folders unique index gains deletedAt — without it, a trashed folder keeps blocking its own name and recreating it fails with a duplicate-key error.
  • The files trashExpiresAt TTL index is dropped — it deleted rows without running the Telegram cleanup.

The script is idempotent, deletes no data, and tells you if duplicates block the new index.

Restart the dev server before testing. Turbopack's watcher does not pick up edits on this mount — stale builds will make correct fixes look broken.
